# SOUL: Android Build

SOUL for Android ships as a directly installed APK from the SOUL website (no Play Store in V1, DECISIONS D-035).

## Machine rules (this workstation)

- **C: is nearly full and hosts the Windows page file.** All caches live on D: (`D:/soul-dev/...`): npm cache, Gradle (`GRADLE_USER_HOME`), Android emulator SDK and AVD, and Docker's disk.
- **15 GB RAM.** Build with the emulator and Docker **stopped**. The build script is memory-capped and stops its Gradle and Kotlin daemons afterwards.
- JDK 17 (`C:/Program Files/Eclipse Adoptium/jdk-17.0.20.1+1`); the system JDK 25 is not used.

## Development build (emulator)

```bash
npm run android:build   # prebuild if needed + x86_64 debug APK, installs if a device is connected
npm run db:start        # local Supabase (Docker, disk on D:)
npm run emulator        # AVD soul_pixel_api36 from D:
npm start               # Metro for the dev client
```

The dev build contains Expo's developer menu. Release builds do not.

## Environment

| Variable | Where | Notes |
|---|---|---|
| `APP_ENV` | build env | `development` or `production` |
| `EXPO_PUBLIC_SUPABASE_URL`, `EXPO_PUBLIC_SUPABASE_ANON_KEY` | `.env` (git-ignored) | the only values bundled into the app |

No secrets ever go into the APK (SECURITY_MODEL section 9).

**Package name:** `com.soul.srm`, locked (C-04) for Android, the future iOS bundle id and the deep-link scheme (`com.soul.srm://`). Development and production builds share it, so on one phone a debug build and a release build replace each other (different signing keys: uninstall first). Never rename it after the public beta without the owner's explicit approval.

## Test APK and production APK (Phase 20)

- Release builds: `./gradlew app:assembleRelease` with all ABIs (`arm64-v8a`, `armeabi-v7a`, `x86_64`).
- Release builds read `.env.production` (cloud Supabase, `APP_ENV=production`). `EXPO_PUBLIC_*` values are inlined into the bundle and Metro caches transformed files, so build releases from a clean cache (the web export already uses `--clear`); otherwise a release can ship the local development URL.
- Signing: see **Signing** below.
- Versioning: `version` (semver) and `android.versionCode` (monotonic integer) in `app.config.ts`, bumped every release.
- Publishing: upload the APK to the site (for example `/downloads/soul-<version>.apk`) and write `/downloads/latest.json` next to it: `{ "version", "url", "sha256", "sizeBytes" }`. The `/download` page reads that file and shows the button, size and SHA-256. Then update `app_config.android_release` (D-039) so installed apps show the update prompt.
- Push: see **Push notifications (FCM)** below.
- Permissions review before release: only what features need. Location is requested only in Instant Meet, camera only for photo capture, notifications after first value.

## Signing (C-20)

Two separate identities:

| Build | Key | Where it lives |
|---|---|---|
| Development (debug) | the Android debug keystore generated by the toolchain | `android/app/debug.keystore` (generated, git-ignored) |
| Production (release) | the SOUL production keystore, one identity forever | outside the repo, e.g. `D:/soul-dev/signing/` plus offline backups |

`plugins/with-release-signing.js` makes release builds read the production key from a local properties file (`SOUL_RELEASE_SIGNING`, default `D:/soul-dev/signing/soul-release.properties`) or from `SOUL_RELEASE_STORE_FILE`, `SOUL_RELEASE_STORE_PASSWORD`, `SOUL_RELEASE_KEY_ALIAS` and `SOUL_RELEASE_KEY_PASSWORD`. **A release build without them fails**; it never falls back to the debug key (Expo's template would, which would make every later update impossible). Keystores, properties files, `signing/`, `.p12` and `.pem` files are git-ignored.

### Creating the production key (not done yet: only when the first release APK is built)

The owner runs this once, on a trusted machine (JDK 17's `keytool`):

```bash
"C:/Program Files/Eclipse Adoptium/jdk-17.0.20.1+1/bin/keytool" -genkeypair -v -storetype PKCS12 -keystore D:/soul-dev/signing/soul-release.jks -alias soul-release -keyalg RSA -keysize 4096 -validity 10000 -dname "CN=SOUL, O=[Operator legal name], C=IN"
```

It asks for one password (PKCS12 uses the same password for the store and the key). Then create `D:/soul-dev/signing/soul-release.properties`:

```
STORE_FILE=D:/soul-dev/signing/soul-release.jks
STORE_PASSWORD=<the password>
KEY_ALIAS=soul-release
KEY_PASSWORD=<the password>
```

### What to preserve, forever

1. `soul-release.jks`, the keystore file.
2. Its password.
3. The alias, `soul-release`.
4. The certificate SHA-256 fingerprint (public; record it here after creation): `keytool -list -v -keystore D:/soul-dev/signing/soul-release.jks`.

### Backup and recovery

- Keep at least **two offline copies** of the keystore in different places (for example an encrypted USB drive and an encrypted cloud or password-manager attachment), and keep the password in a password manager, never next to the file.
- After creating it, test a restore: copy a backup to a temporary folder, point `SOUL_RELEASE_STORE_FILE` at it, build a release APK, and check the fingerprint matches (`apksigner verify --print-certs`).
- **If the key is lost:** installed apps can never be updated again. The only way forward is a new package name and asking every user to reinstall, which breaks the C-04 lock. This is why backups matter.
- **If the key leaks:** someone could sign fake updates. Rotate with APK Signature Scheme v3 key rotation (`apksigner rotate` to create a signing lineage from the old key to a new one, then sign releases with the lineage), publish the new fingerprint on `/download`, and tell users. This needs the old key, so backups matter here too.

## Push notifications (FCM, C-16)

FCM works for APKs installed outside Google Play; it needs Google Play services on the phone (most Android phones in India have them), not a Play Store listing. Push is optional: SOUL works fully without it.

What the owner creates (Phase 14 is built; this switches Android push on):
1. A Firebase project (free) and an **Android app** in it with package name `com.soul.srm`.
2. Download `google-services.json` and place it at the repo root (git-ignored). `app.config.ts` picks it up automatically when the file exists; rebuild with `CLEAN=1 npm run android:build`.
3. A **service account key** (Project settings → Service accounts → Generate new private key). Never commit it; it goes to the server with `supabase secrets set FCM_SERVICE_ACCOUNT="$(cat key.json)"`, and the Edge Function sends through the FCM HTTP v1 API.

## Status

The development build works on the emulator (Phase 4 verified end to end). Release signing and the production APK are Phase 20.

**Rebuild after font changes:** fonts are embedded at build time, so a change in `assets/fonts` (the body font or the SoulIcons subset) needs `npm run android:build` (`CLEAN=1` regenerates `./android` when `app.config.ts` changed).
